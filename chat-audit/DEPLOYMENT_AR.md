# إصلاح ونشر موقع HUB للدردشة

## نتيجة الفحص

الواجهة مبنية بـ React/Vite، لكنها تعتمد كذلك على خادم Express مكتوب في `server.ts`. الخادم يوفر:

- واجهات الرسائل والمزامنة تحت `/api/...`.
- اتصال WebSocket دائم على `/ws` للحضور الفوري والصوت المباشر.
- رفع ملفات الصوت والصور وحفظ بيانات محلية.

لذلك، نشر مجلد الواجهة المبني `dist` وحده على Netlify لا يشغّل `server.ts`. حينها تتجه طلبات `/api/...` و`/ws` إلى موقع Netlify نفسه حيث لا يوجد هذا الخادم. الكود يتجاهل أخطاء الشبكة في عدة مواضع، فيبدو أن الإرسال تم محليًا لدى المرسل بينما لا يصل إلى بقية المستخدمين. وهذا يفسر تعطل الكتابة والصوت معًا.

الصوت المباشر يحتاج أيضًا إذن الميكروفون واتصال HTTPS؛ Netlify يوفر HTTPS عادةً، لكن HTTPS وحده لا ينشئ خادم WebSocket.

## إصلاحات أُجريت

1. تحديث اعتماد `esbuild` ليتوافق مع إصدار Vite الموجود بالمشروع؛ كان `npm install` يفشل بتعارض إصدارات قبل التحديث.
2. جعل الخادم يقرأ `PORT` من بيئة الاستضافة بدل تثبيت المنفذ على 3000 فقط.
3. إضافة هذا الدليل وخطوات النشر.

## مسار النشر الأبسط

انشر **المشروع كاملًا كخادم Node.js** على منصة تشغّل عمليات Node طويلة الأمد وWebSocket، بدل نشر الواجهة وحدها على Netlify. في إعدادات الخدمة استخدم:

- أمر البناء: `npm ci && npm run build`
- أمر التشغيل: `npm start`
- إصدار Node: 22 أو إصدار متوافق مع الاعتماديات الحالية.
- افحص الخدمة بعد النشر عبر `https://عنوان-الخدمة/api/health`، ويجب أن تعيد JSON يحتوي على `status: "ok"`.

الخادم يقدّم ملفات الواجهة المبنية بنفس النطاق، لذلك تبقى مسارات `/api/...` و`/ws` متجهة إلى الخادم الصحيح دون تعديل إضافي في الواجهة. تأكد في لوحة المضيف من أن WebSocket مسموح.

### ملاحظة حفظ البيانات

الخادم الحالي يخزن بعض البيانات والملفات محليًا في مجلد `data/`. بعض مضيفي التطبيقات يمسحون القرص المحلي عند إعادة التشغيل أو لا يجعلونه دائمًا. فعّل قرصًا دائمًا واربط مجلد `data` به إذا كانت المنصة توفر ذلك، أو انقل التخزين إلى قاعدة بيانات وFirebase Storage/S3 قبل الاعتماد على الخدمة للإنتاج. التصميم الحالي لخادم الحالة يفترض نسخة خادم واحدة؛ لا تشغّل عدة نسخ متوازية دون نقل الحالة إلى مخزن مشترك.

## إذا رغبت في الإبقاء على Netlify

يلزم إبقاء الواجهة على Netlify ونشر خادم Node/WebSocket منفصل على مضيف مناسب، ثم تعديل إعداد الواجهة لتستخدم عنوان الخادم المنفصل لجميع `/api/...` وعنوان `wss://.../ws` لاتصال WebSocket، مع إعداد CORS وOrigin المناسبين. ملفات المشروع الحالية لا تتضمن هذا الفصل أو عناوين API عامة. تحويل Express إلى Netlify Functions قد يخدم بعض طلبات HTTP، لكنه لا يحوّل خادم WebSocket المستمر إلى Function؛ الصوت الحي والحضور يحتاجان WebSocket service أو خدمة realtime متخصصة.

## إعداد Firebase

رسائل Firestore المباشرة تعمل فقط عندما يكون المستخدم مسجّلًا فعليًا عبر Firebase Auth وتسمح قواعد Firestore بالكتابة له. تسجيل الدخول المحلي/الحسابات التجريبية في الواجهة لا ينشئ جلسة Firebase Auth، لذا يعتمد هذا المسار على خادم Node في المشروع. افحص Firebase Console إذا استمر فشل تسجيل الدخول إلى Google أو Firestore بعد إصلاح الاستضافة:

- إضافة نطاق الموقع المنشور إلى Firebase Authentication > Authorized domains.
- تفعيل مزود Google إذا كان تسجيل الدخول به مطلوبًا.
- نشر قواعد Firestore المطابقة للمشروع ومراجعة سجل Console في المتصفح؛ لا تجعل القواعد عامة لمجرد تجاوز الرفض.

## التحقق المنفذ

- `npm install --no-audit --no-fund`: نجح بعد تحديث اعتماد esbuild.
- `npm run build`: نجح.
- `npm run lint`: نجح دون أخطاء TypeScript.

نجاح البناء لا يختبر إعدادات حساب Netlify أو Firebase الفعلية؛ يجب نشر الخادم والتحقق من `/api/health` ثم تجربة موقعين/جهازين مختلفين.
